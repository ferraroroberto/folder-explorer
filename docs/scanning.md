# Scanning: metadata only, never a download

How a scan reads every file's size without opening a file, why that keeps OneDrive placeholders online-only, and the index it writes.

## The listing

`src/winfs.py` opens each folder once, with `CreateFileW(FILE_LIST_DIRECTORY, FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT)`, and pages `GetFileInformationByHandleEx(FileFullDirectoryInfo)` in 64 KiB pages. Every record carries:

| Field | Becomes |
| --- | --- |
| `EndOfFile` | **Size**: the logical length, what the cloud stores and what a download would fetch |
| `AllocationSize` | **On disk**: the bytes allocated on this volume (0 for an online-only file) |
| `FileAttributes` | the cloud state and whether the entry is a folder or a reparse point |
| `EaSize` | the reparse tag, on a reparse point |
| `LastWriteTime` | the modified date |

No file is opened, read or stat-ed one by one: one handle per folder gives every figure. That is also about a hundred times faster than a `GetCompressedFileSizeW` call per file. Off Windows the same record comes from `os.scandir` + `lstat`, with `st_blocks` as the allocation.

## Cloud files

A file is **online-only** when any of `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, `FILE_ATTRIBUTE_RECALL_ON_OPEN` or `FILE_ATTRIBUTE_OFFLINE` is set; the OneDrive client marks its placeholders with the first. `FILE_ATTRIBUTE_PINNED` means "always keep on this device". Opening a placeholder's *data* is what makes the sync client download it, and a scan never does. Listing a folder whose listing is not local yet may make the client fetch that listing, which is metadata, never file content.

Checked on a real online-only document before and after full walks of its tree: attributes `ARCHIVE | RECALL_ON_DATA_ACCESS` unchanged, `GetCompressedFileSizeW` 0 throughout.

## Links

A folder whose reparse tag is a name surrogate (a junction, a symlink, a mount point) is counted in `skipped_links` and never followed, so no bytes are counted twice and no walk loops. OneDrive's own cloud reparse tags are not name surrogates, so synced folders are walked normally.

## The index

One SQLite file per finished scan, `index/<root>-<scan id>.sqlite3` in the runtime-data folder. The walk is depth first, so folder ids are pre-order and each folder's subtree is the id range `[lo, hi]`; every "under this folder" question is a range scan.

| Table | Rows |
| --- | --- |
| `folders` | id, parent, name, depth, `lo`/`hi`, subtree totals (size, alloc, files, folders, online-only files and bytes, listing errors), and `hidden` |
| `files` | folder id, name, extension, size, alloc, attributes, modified time, and `hidden` |
| `folder_ext` | per folder and extension, the folder's *own* files: size, alloc, count, online-only count and bytes; a subtree's type totals sum a range of it |
| `folder_paths` | each folder's full path, case-folded, accents dropped, with `/` separators: what folder search matches every word against |
| `folder_words` | each word of the folder names (folded the same way) with the ids of the folders whose own name holds it, packed: where folder search finds a near word's folders |
| `folder_people` | folders holding subfolders named like email addresses, with how many: folder search's "folder of people" |

Folder search scans `folder_paths` with `instr`, one call per word, where a trigram FTS index would triple the index size for little gain. When the exact hits leave room in the results, a word of six letters or more also looks for its near words: its one-edit spellings are looked up in `folder_words` by key (a spelling or a word starting with it), and only the subtrees under those folders are read, never every path again. On 2.6 million folders `folder_words` adds about 3% to the index. An index written before `folder_words` stores paths case-folded only; it is searched for each word as typed and folded, with no near words, until the next scan replaces it. One written before `folder_paths` answers folder search with "rescan".

`hidden` is 0 for a visible item, 1 for one with the hidden or system attribute (both come with the listing, so nothing extra is read), and 2 for anything inside a hidden folder. Explore leaves out every nonzero row unless its Hidden items switch is on. The totals count every row either way. An index from before the column lists everything, and Explore says a rescan would tell hidden items apart.

The index is built as `<name>.part` and renamed into place only when the walk finishes. `state.sqlite3` records each scan (root, trigger, live counters while it runs, status, index file); a root's current index is its newest scan that finished `ok`. A failed or interrupted scan leaves the previous index in place, and the page flags the root. Replaced index files are deleted once no reader has them open.

## The email stage

Each scan ends with the email stage, `python -m app.cli email index` in its own process. Its manifest of `.msg` files comes from the scan's own index (the `files` rows with extension `msg` under each email folder), so nothing is listed twice; a scoped run (`--root <folder>`) lists only that folder with the same handle listing. The stage diffs the manifest against `emails.sqlite3` by path, size and modified time and reads only what is new, changed, or indexed before To, Cc, attachments and size were stored. The stage first decides every file's verdict without opening anything, so it knows how many files need a read (`to_index`) before the first read; while it reads it hands its counts so far (`done`, `downloaded`, `downloaded_bytes`, `failed`, `waiting`) to `src/store.py`, which keeps them on the running `email_runs` row at most once a second for the Scans tab. An online-only file is read (and so downloaded) without limit by default (`email.download_budget_mb` `null`); with a number set it is read only while the run's download budget lasts. A file that fails is recorded in `email_failures` with its size and modified time and skipped until either changes. Rows for files the manifest no longer lists are removed only when the folder's listing had no errors. Excluded folders are skipped by the walk, so they never reach the manifest; `email.exclude` folders are dropped from a manifest read from the scan index too, since the disk walk does not skip them. The stored `body_preview` is the readable text only: `src/email/preview.py` drops the `<url>` link targets, `[cid:…]`/`[image]` placeholders and URL-only lines Outlook writes into a plain-text body, before the preview is cut, on both the `.msg` read and the live mailbox read. Each run first cleans any stored preview that still carries that markup from its own text (no file is opened, so no download), and the search index follows.

`emails.sqlite3` keeps the layout the consumers read: the `emails` columns, `emails_fts(subject, sender, recipients, body_preview)` in that order, `recipients` still holding the To line, plus `to_addrs`, `cc_addrs`, `attachment_names`, `has_attachments` and `size`. It is a WAL database; the stage is the only writer that reads a `.msg`. Filing a mail (the Archive sheet and window, the batch `apply`) also writes that mail's row at once, from Outlook's own facts, with the modified time at 0 and `to_addrs` empty, so the mail reads as archived straight away and the next stage run reads the file once and completes the row; `revert` and `renumber` keep rows true to the files they changed. Every reader opens it read-only.

The disk walk holds `scan.lock`, the email stage `email.lock`, both OS byte-range locks the system drops when the holder exits. A run waiting on the email lock past its `--wait` exits 2 ("busy"), never a plain failure. Each run writes a row to `email_runs` in `state.sqlite3` with its counts.

## Running the email index

With `email.roots` set (the email folders, each inside a scan root) and `email.index_path` left empty, the app keeps its own email index, `emails.sqlite3` in the runtime-data folder, and is its only writer. Every scan ends with the email stage: it compares the scan's list of `.msg` files with the index by path, size and modified time, reads only new or changed mail through `src/email/reader.py`, and removes rows for mail that is gone only after a complete listing of its folder. It opens only a `.msg` inside `email.roots` (see What opens a file, below). Reading an online-only mail downloads it, so by default one run downloads everything it needs (`email.download_budget_mb` is `null`, "No limit"). A whole number caps one run at that many MB and leaves the rest for the next run ("waiting for budget"); 0 reads local files only. A budget saved in `config.json` is kept as it is, so a config that already holds a number stays capped until Settings → Email folders → OneDrive downloads per run is switched to "No limit (recommended)". A file that fails is not read again until it changes. `email.exclude` (Settings → Leave out of the email index) names folders inside the email folders that only the email index skips; the global skip list applies to it too. The Scans tab shows each run (new, downloaded, failed, and waiting for budget when a cap is set) and runs it now, or for one folder; a run of every folder started there lists the email folders afresh (`--fresh`), so mail filed since the last disk scan is read too. While a run is going its row shows a bar over the files that need a read, with the files done, the files and MB downloaded, the failed reads and the files left unchanged, refreshed every 2 seconds; the stage stores those counts on the running row of the run history, so the page reads them from `GET /api/email/status` (`runs[0].counts`, plus `budget_mb`):

- `& .\.venv\Scripts\python.exe -m app.cli email index` (every email folder) or `... email index --root <folder>` (one folder below one, in seconds, under the email lock only, so it never waits behind a disk scan). Exit 0 indexed, 1 failed, 2 busy (another email run held the lock past `--wait S`), 3 not inside an email folder, 4 not set up here.
- `... email import --from <emails.db>` copies another app's email index in once, keeping its rows; the next run reads each mail once more to fill To, Cc, attachments and size. `... email status` lists the last runs.
- `... email subjects [--root <folder>] [--limit N]` is a dry run that lists archived mails whose file name lost its first letters to an old reply-prefix rule ("Recibo" filed as "cibo"): a count and N names, printed locally. It reads each mail's subject under the email stage's download budget and lock, and renames nothing. `email batch fix-cut-names` renames those files to the full subject: a dry run unless `--apply`, with the date and sequence kept, no file overwritten (a taken name is counted as a clash), the index rows following the rename and an undo log (`cut-names-undo-<time>.json`, written before the first rename) in the runtime-data folder; `--revert <log>` restores from it. The disk walk's tree shows the new names after the next scan.
- `... email index --fresh` lists the email folders now instead of reading the last scan's index: a mail filed since that scan is only seen this way.
- `... scan --no-email` scans the disks only.

Downloaded mail stays on the disk until OneDrive frees it. The app never sets a file back to online-only, because that is a write.

## What opens a file

The disk walk never opens a file. Mail is one exception: a `.msg` inside the email folders (`email.roots`), opened by five callers, all through `src/email/reader.py`:

- the email stage, on every scan and on `email index`;
- Show all in the Search preview, for the single mail you pick;
- `email batch renumber`, when the index lacks a mail's date or attachment names;
- `email subjects`, the dry run that lists names cut by an old rule;
- `email batch fix-cut-names`, the rename that follows from it.

The document viewer is the other exception: a `.md`, `.markdown`, `.html` or `.htm` file up to 2 MB, the images beside it that it shows (`.png .jpg .jpeg .gif .webp .svg`, up to 10 MB), and for an HTML page the stylesheets and scripts beside it (`.css .js`, up to 2 MB each), read only through `src/docs/reader.py` when someone opens the document in Explore's sheet or the `/doc` window. The file is named by root, scan id and item id; its path is rebuilt from the scan. Before any byte is read, a fresh listing of its folder (the same directory handle the scan uses) checks that it is still there, is not a link, is under the cap, and is not cloud-only. A cloud-only file is refused with "Only in OneDrive", and the open asks Windows not to recall data (`FILE_FLAG_OPEN_NO_RECALL`), so a placeholder the listing missed fails instead of downloading. **Download and open** (and an image's own Download) is the one path that brings a cloud-only file down: one file, on a tap. A relative link or image in a document resolves on the server against the document's folder and must stay inside its root; one that leaves it, or that the scan did not see, renders inert. Rendering reads nothing from disk, and neither does the editor's draft preview, which renders the text the page sends.

An HTML page is not rendered by the server: `src/docs/html_frame.py` rewrites only the start tags that name a file. A relative stylesheet, script or image, found by the same root-fenced lookup and read through the reader (a cloud-only one is never downloaded, only skipped), becomes a `data:` address, with 10 MB inlined per page at most; a relative link to a scanned Markdown or HTML file becomes its `/doc` address by id, and any other relative link goes inert. The page draws in an `iframe` whose `srcdoc` is that text, sandboxed with `allow-scripts allow-popups allow-popups-to-escape-sandbox` and without `allow-same-origin`, so its scripts run in an opaque origin that can't read the app's page, cookies or storage. Its requests to the app carry `Origin: null` (CORS) or `Sec-Fetch-Site: cross-site` (no-cors), and the sign-in gate refuses both on every `/api/` path, loopback included. With **Block remote content in HTML** on, a Content-Security-Policy at the top of the frame allows only inline and `data:` content, so nothing loads from the web.

A Markdown or HTML file dropped on the window from File Explorer gives the page its bytes and name, never its path. The page sends the name, size, modified time and a SHA-256 of the bytes made with Web Crypto (`POST /api/doc/dropped/match`; a page not served securely has no Web Crypto and sends no hash). A name that is a path, or a hash that is not 64 lower-case hex digits, is refused. The server answers in this order, and the first step that finds exactly one file wins:

1. **The index.** One indexed document with that name (any case), size and modified time (within a second, since a browser reports milliseconds and the index whole seconds). Nothing on disk is read.
2. **Edited since the scan.** For a caller on this PC with a hash: every indexed file of that name, whatever its size. Each is read through the reader above (a fresh listing of its folder, the size cap, the cloud check) and hashed; exactly one equal file opens as its indexed id, so Edit saves against the file as it is now. The reader is asked for no more bytes than the dropped file has, so a file of another size costs a listing only.
3. **Not scanned yet.** If no indexed file matched: a fresh listing of the scanned folders, those that hold a Markdown or HTML file first (newest first), then the others in scan order, looking for the name. A file of the same size is read and hashed; the one equal file opens under a lasting negative id (the same record the "Open with" launcher keeps). Every folder comes from the index, so a candidate is never outside a configured root, and one physical file listed under two roots (a synced library on a local drive) counts once.

Steps 2 and 3 share one budget of 4 seconds and 3,000 folders listed, and each lookup writes one info line (outcome, step, candidates read, folders listed, cloud-only skipped, milliseconds, never a name or a path). A file that is only in OneDrive is never downloaded to compare; it is counted and the answer is `not_confirmed`.

When no one file is found the answer is `match: null` with a `why`: `several` (two or more equal files, or two indexed files with the same name, size and time and no hash to tell them apart), `not_found` (none in the scanned folders, or the budget ran out first) or `not_confirmed` (a cloud-only candidate, no hash from the page, or a caller off this PC, which never reaches steps 2 and 3). The page then reads the file itself and sends the text (`POST /api/doc/dropped/render`, up to 2 MB): the server renders it read-only from that text, reading nothing from disk, with relative links and images inert because the file has no folder here, and a toast names the reason. Such a file cannot be edited or saved, as the writer only saves a file the scan or the lookup named. Dropped on the app, either kind opens in its own `/doc` window: the window is opened inside the drop (so the browser counts it as the reader's own act) and pointed at the document's address once the match answers. A rendered file has no address, so the app page keeps the rendered document and the new window, at `/doc?dropped=<token>`, asks it for the document over `postMessage` between the two same-origin windows; the page gives it out once, to the window it opened, and drops it after a minute. The text is never in an address, and nothing is stored on the server or the device. Reloading that window finds nothing and says to drop the file again. A blocked window opens the file in the app's sheet instead.

The "Open with" launcher (`python -m app.launcher <file>`, registered by Settings' **Associate Markdown files with this app**) opens nothing itself. In its own process it matches the path Windows hands it against the configured roots and reads the root's current index (read-only) for the file's folder, then asks the running app over loopback (`POST /api/doc/find`, refused to any caller but this PC) with the root, scan id, folder id and file name, never the path. The app answers from the index; a file the scan has not seen yet, in a folder it has, is found in one fresh listing of that folder (the same directory handle, no file opened) and keeps a lasting negative id for that scan in `state.sqlite3`. A file in a folder the scan does not know is not opened: the launcher says to run a scan. The document then opens in the `/doc` window, through the reader above like any other.

The document editor is the one writer of a user's file outside the email folders, only through `src/docs/writer.py`. It writes the one `.md`, `.markdown`, `.html` or `.htm` file it opened, named by root, scan id and item id like every read: never a new file, never another one, never a link or a cloud-only placeholder. A file over 1 MB, or not UTF-8, opens read-only. Save sends the version the editor opened (the listing's modified time, the size and a hash of the bytes served); the writer reads the file again through `src/docs/reader.py`, so every check above applies, and refuses on any difference with "Changed on disk since you opened it". Only **Overwrite theirs…**, after its confirm sheet, replaces that newer copy, and it first keeps it in the runtime-data folder under `doc-backups/`. The new bytes go through `src/atomic_write.py` (a temporary file beside the document, then one rename) and keep the file's byte-order mark, line ends and final newline; a save of unchanged text writes nothing.

Nothing else opens or writes a scanned file. Filing mail (the Archive sheet, the macro, the archive verbs) writes only inside `email.roots`: [archive.md](archive.md). Explore's open actions read nothing; they hand a path to Windows.

## One scan at a time

`scan.lock` in the runtime-data folder is an OS byte-range lock taken without waiting, by the app's Rescan, the in-app schedule, the tray and the CLI alike. The operating system releases it when the holder exits, so a crashed scan never leaves it stuck; the next scan marks the crashed one `interrupted`.
